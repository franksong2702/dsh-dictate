# 语音输入状态焦点卡片：交互设计规格

状态：已实施，待真实麦克风体验验收
适用范围：`dsh-dictate` 的 Web Speech 与本地 ASR 两种识别方式
最后核对：2026-08-24，DSH `0.1.1-rc.2`

## 1. 要解决的问题

当前语音信息条一次只保存一个状态。状态切换后，上一条信息会消失，因此用户难以回答：

- 本次录音已经持续了多久；
- 8 分钟后的结束倒计时是否仍在当前状态中清楚可见；
- 当前是在录音、转写、确认还是润色；
- 某个阶段是完成了、失败了，还是被后续文案覆盖了；
- Web Speech 与本地 ASR 为什么在相同操作下显示不同信息。

本设计把单行状态条改为锚定 Composer 的“语音处理焦点卡片”。界面只显示当前阶段，不把内部阶段历史暴露给用户；浮层不参与页面排版，因此不把聊天记录向上推。

## 2. 设计目标

1. Web Speech 和本地 ASR 使用同一套阶段、布局、录音时长和安全规则。
2. 用户始终能在同一个视觉焦点内区分当前状态和非最终文字。
3. 倒计时等重要信息不会被下一次识别回调覆盖。
4. 浮层不改变 Composer 和聊天记录的布局高度。
5. 不把端口、音频分段、模型请求等内部实现暴露给普通用户。

## 3. 非目标

- 不把浮层做成本地 ASR 或 Web Speech 的调试日志。
- 不在本功能中恢复浏览器内 WASM ASR。
- 不因为采用共同交互而强制两种识别方式具有相同的过程文字能力。
- 不在本轮设计中改变 8 分钟提醒、9 分钟自动停止和“自动停止不自动发送”的既有规则。
- 不保存跨录音、跨会话或跨浏览器重启的历史记录。

## 4. 实施前核对的技术边界

- 实施前 `TranscriptionDock` 注册到 `conversation.input.dock`，属于 Composer 上方的正常文档流；增加行数会增加 Composer 区域高度。
- DSH 同时提供 session-scoped 的 `conversation.input.overlay` 列表插槽。
- Composer 内已有绝对定位的 `overlayAnchor`，官方斜杠菜单和模型选择弹窗也使用这个锚点。
- 实施前 `transcriptionStore` 每个 session 只保存一个 `TranscriptionSnapshot`，更新采用覆盖/合并，而不是事件累积。

结论：浮层已在插件内实现，无需修改 upstream DSH；内部仍可记录关键事件用于诊断，但用户界面只渲染当前状态。

## 5. 信息结构

浮层只显示一个当前焦点卡片。进行中和结束后分别使用进行时与完成时：

```text
录音进行中：
┌──────────────────────────────────────────┐
│ ● 正在录音中  已持续 00:24               │
│                 再次点击麦克风结束       │
└──────────────────────────────────────────┘

录音结束并完成润色后：
┌──────────────────────────────────────────┐
│ ● 已润色完成  最终结果已写入输入框       │
└──────────────────────────────────────────┘
┌──────────────── Composer ────────────────┐
│ 给智能体发消息……                         │
└──────────────────────────────────────────┘
```

### 5.1 内部事件

- 用户界面不显示历史事件，不出现“录音已结束”和当前转写/润色同时竞争注意力的情况。
- 内部可以继续记录停止原因、阶段耗时和错误，供测试与诊断使用。
- 8 分钟提醒、9 分钟停止原因和错误都在当前卡片原位更新，不新增第二层消息。
- 内容超过浮层高度时，当前状态和过程文字共用同一个纵向滚动窗口。
- 默认自动跟随最新识别文字；用户主动向上滚动后暂停跟随，回到底部后恢复。

### 5.2 当前状态

- 当前卡片始终是浮层内唯一的视觉焦点。
- 主文案继续遵守五个字规则。
- 辅助文案描述用户下一步或系统正在做什么。
- 录音期间辅助文案使用 `已持续 mm:ss`，不重复主文案中的“录音”。
- 用户主动停止后直接切换为转写或确认状态，不重复显示“录音已结束”。
- 达到 9 分钟上限时，在当前辅助文案说明自动停止原因。

### 5.3 可选过程文字

- 它不是时间线事件，不会因为每次识别回调而产生新行。
- Web Speech 可以显示 `实时识别（非最终）`。
- 本地 ASR 录音期间不显示后台分段文字。
- 本地 ASR 停止后，如已有稳定分段结果，可显示 `初步转写（非最终）`，直至最终结果写入 Composer。
- 最终文字只出现在 Composer；浮层不得暗示过程文字已是最终结果。

## 6. 共同状态机

| 共同阶段 | 主文案 | 可见历史消息 | Web Speech 辅助文案 | 本地 ASR 辅助文案 |
|---|---|---:|---|---|
| 准备麦克风 | `等待授权中` | 否 | `请按浏览器提示允许麦克风访问…` | 相同 |
| 录音/识别 | `正在听写中` / `正在录音中` | 否 | `已持续 mm:ss · 请开始说话…` | `已持续 mm:ss · 再次点击麦克风结束并转写` |
| 检测到语音 | 主文案不变 | 否 | 不单独显示 | `已检测到语音` |
| 8 分钟倒计时 | 主文案不变 | 否 | `已持续 08:00 · 01:00 后自动结束并转写` | 相同 |
| 用户停止 | `正在确认中` / `正在转写中` | 否 | `正在确认识别结果，请稍候…` | `正在处理录音，请稍候…` |
| 9 分钟停止 | `正在确认中` / `正在转写中` | 否 | `已达到 9 分钟上限，正在确认识别结果…` | `已达到 9 分钟上限，正在处理录音…` |
| 转写完成 | 进入下一阶段 | 否 | 相同 | 相同 |
| 润色 | `正在润色中` | 否 | `初步转写不是最终结果；完成后将写入输入框或直接发送` | 相同 |
| 完成 | `已转写完成` / `已润色完成` | 否 | 说明写入 Composer 或直接发送 | 相同 |
| 失败 | `转写未完成` / `润色未完成` | 否 | 可重试或保留原始结果 | 相同 |

说明：两种识别方式共享阶段含义，但不强行统一主文案中的“听写”和“录音”。这两个词分别反映 Web Speech 的实时识别和本地 ASR 的录音后汇总行为。

## 7. 事件生成与更新规则

### 7.1 可见历史事件

- 不新增。阶段变化只更新当前焦点卡片。

### 7.2 不应新增事件

- 每秒倒计时刷新；
- 麦克风开始采集；
- 进入 8 分钟倒计时；
- 开始最终转写或确认；
- 开始润色；
- 短于 3 秒的过程状态；
- Web Speech 的每次 interim/final 回调；
- Web Speech 为维持同一次逻辑听写而进行的自然重启；
- 本地 ASR 每个 25 秒音频分段的创建、排队或响应；
- 本地服务端口、模型锁、请求序号等诊断信息；
- 同一阶段重复上报的相同状态。

### 7.3 原位更新

- 倒计时只使用固定 current row，在 `01:00` 到 `00:01` 之间原位更新，不创建历史事件。
- 当前阶段的辅助文案使用固定 current row 更新。
- 非最终文字使用固定 preview row 更新。
- 相同错误在同一次录音中只保留一条。

## 8. 浮层布局与层级

- 从 `conversation.input.dock` 迁移到 `conversation.input.overlay`。
- 浮层锚定在 Composer 上沿，向上展开，不覆盖 textarea、工具按钮或发送按钮。
- 宽度与 Composer 卡片一致；窄窗口两侧至少保留 12 px。
- 最大高度 180 px；超过后整个信息区纵向滚动，自动跟随最新内容。
- 浮层只包含当前状态卡片，不叠加历史消息层。
- 当前状态卡片包含状态主文案、辅助文案、非最终转写和操作按钮；长过程文字在卡片内部滚动。
- 背景使用完全不透明的二级背景色，避免下方 Composer 内容透出并干扰信息辨识。
- 推荐层级低于 DSH 官方菜单。斜杠菜单或模型选择弹窗打开时，它们覆盖语音浮层，而不是被语音浮层遮挡。
- 浮层只在自身边界内接收滚轮、触控和键盘滚动，不影响下方 Composer；完成态开始收起后立即停止接收指针事件。
- 活跃录音期间浮层保持展开。完成态向下收起后不留下占位空间。

## 9. 动效

- 当前卡片首次出现时从底部轻微进入，时长 160–220 ms；阶段原位更新不产生第二张卡片。
- 倒计时数字更新不触发行位移动画。
- 完成态短暂停留后向下滑入 Composer，由 Composer 上沿裁切收起，不使用淡出。
- 系统开启 `prefers-reduced-motion` 时取消位移动画，只保留即时状态变化。
- 录音阶段使用低幅度红色呼吸灯，准备、转写和润色阶段使用低幅度蓝色呼吸灯，周期为 1.6 秒；圆点本身保持稳定，只让外围光晕变化，避免 9 分钟录音期间持续抢夺注意力。
- 完成阶段的绿色状态灯只播放一次 440 ms 确认动画，随后保持常亮直到信息条收起；错误红灯保持静止。状态变化不能只靠颜色表达。

## 10. 无障碍

- 当前阶段使用 `role="status"` 与 `aria-live="polite"`。
- 错误使用 `role="alert"`。
- 视觉倒计时可以每秒更新，但屏幕阅读器只在剩余 60、30、10、5、4、3、2、1 秒时播报，避免 60 次连续播报。
- 时长数字使用等宽数字，但不能只靠颜色表达完成/失败状态。
- 整个浮层获得键盘焦点后允许滚动；默认不抢夺 Composer 焦点。

## 11. 生命周期与清理

- 事件只属于当前 session 和当前一次录音。
- 新录音开始时清空上一轮时间线。
- 用户中途取消时立即结束当前活动状态；若没有结果，浮层收起并清理。
- 完成态保留约 3.5 秒，再用约 0.5 秒向下收起。
- 错误态在用户重试、切换识别方式或主动关闭之前保持可见。
- session 切换或组件卸载时取消计时器、订阅和动画回调。

## 12. 建议的数据契约

```ts
type VoiceTimelineEvent = {
  id: string
  elapsedMs: number | null
  phase: 'recording' | 'stopping' | 'transcribing' | 'polishing' | 'complete' | 'error'
  label: string
  detail: string
  tone: 'current' | 'complete' | 'warning' | 'error'
  updateKey?: 'current' | 'preview'
}

type VoiceTimelineSnapshot = {
  current: VoiceTimelineEvent | null
  history: readonly VoiceTimelineEvent[] // 仅用于内部诊断，不参与 UI 渲染
  previewLabel: '实时识别（非最终）' | '初步转写（非最终）' | ''
  previewText: string
  action: TranscriptionAction | null
}
```

约束：`history.length <= 12` 且不得在用户界面渲染；相同 `updateKey` 的事件原位更新；过程文字不得写入 `history`。

## 13. 验收标准

1. Web Speech 与本地 ASR 都在同一浮层组件中呈现共同阶段。
2. 当前卡片因过程文字增长时，聊天滚动区和 Composer 的布局高度不发生变化。
3. 08:00 到 09:00 的倒计时只更新当前状态，且识别回调不能覆盖倒计时。
4. 09:00 自动停止后，当前辅助文案说明达到时长上限，界面不显示历史消息。
5. Web Speech 自然重启不会出现在时间线，也不会结束逻辑听写。
6. 本地 ASR 的音频分段不会出现在时间线。
7. 本地 ASR 录音期间不展示分段识别文字。
8. 所有过程文字都明确带有“非最终”标识。
9. 自动停止在开启自动发送时仍不触发发送。
10. 官方斜杠菜单和模型选择弹窗可以覆盖语音浮层，并保持可操作。
11. 屏幕阅读器不会每秒播报整个倒计时。
12. 新录音、取消、session 切换和卸载均不会留下上一轮状态或计时器。

## 14. 已批准决策

### D1. 完成态保留多久

决定：完成后保留约 3.5 秒，再用约 0.5 秒向下滑入 Composer。理由是结果已经进入输入框，继续停留 8 秒显得迟钝；短暂停留足够确认结果，同时下收动作比淡出更符合信息回到 Composer 的空间关系。

### D2. 是否显示历史消息

决定：不显示。内部最多保留 12 条诊断事件，但用户界面始终只有一张当前焦点卡片。

### D3. 是否提供展开/收起

决定：第一版不提供手动展开/收起。活跃时自动展开，完成后自动消失。理由是先验证时间线本身的价值，避免增加一个需要学习的新控件。

### D4. Web Speech 非最终文字放在哪里

决定：放在当前状态下方的独立 preview row，不进入历史。理由是文字更新频率远高于阶段更新，混在时间线中会造成视觉跳动。

### D5. 浮层与官方菜单同时出现

决定：官方菜单层级更高，临时覆盖浮层；语音状态继续后台更新。理由是菜单属于当前主动操作，优先级高于被动状态信息。

### D6. 阶段变化如何呈现

决定：在同一张当前卡片内原位切换，不把完成时事件展示到卡片上方。理由是上下同时出现新信息会形成两个视觉焦点。

### D7. 8 分钟提醒如何呈现

决定：只更新当前辅助文案。提醒是一瞬间动作，不新增第二层消息。

### D8. 短暂过程如何呈现

决定：短于 3 秒的转写、确认等过程可以原位更新当前状态，但不在界面留痕。理由是毫秒级或一两秒的内部切换不是用户需要回看的阶段。
